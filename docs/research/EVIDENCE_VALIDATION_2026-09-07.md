## Executed checks

Checks covered:

## Where native TRT chunk time goes

Population: all 550 chunks in five ten-job repetitions, arithmetic mean of each recorded `stages_ms` field. Summed mean interval time: **794.337 ms/chunk**.

| Phase grouping | Mean ms/chunk | Share of summed recorded phases |
| --- | ---: | ---: |
| Four DiT steps | 441.026 | 55.52% |
| VAE decode | 213.082 | 26.83% |
| Nine-frame motion encoding | 73.114 | 9.20% |
| Color correction | 23.785 | 2.99% |
| Reference-mode allocator-release interval | 17.533 | 2.21% |
| Audio encoding | 14.250 | 1.79% |
| Conditioning, quantization, transfer and other intervals | 11.547 | 1.45% |

Rounding means displayed percentages need not sum exactly to 100%. The `dit_offload` label in this **reference-mode TRT** run covers allocator release, not moving DiT weights. In the older **staged** true-9:16 run, offload+reload averaged 923.076 ms/chunk and did include device movement. Label semantics depend on execution mode and source revision.

Instrumented phase intervals and full wall times have different accounting boundaries. Do not calculate useful FPS as 33 divided by phase time: nine frames are overlap and the final chunk also includes excess. Do not add stage speedup percentages.

The plan's hypothetical Amdahl examples are recomputed in the notebook. For example, halving DiT time with everything else fixed yields about 1.384× phase-time throughput, not 2× whole-model FPS. No such improvement has yet been measured.

## Calls: correct denominator and pass meaning

[Thirty-minute generated-idle soak](../../benchmarks/implementation/calls-generated-idle-soak30m.json):

- Wall time 1819.820635 seconds, 209 completed turns, 210 turn IDs including interruption, 60 resource samples.
- Transport and cleanup passed; 23 underrun slots were still counted.
- Server snapshot: 45,470 sent frames, 10,535 held frames, 34,944 generated frames including 14,856 neural-idle frames.
- Held fraction at that snapshot: **10,535 / 45,470 = 23.1691%**.
- Receiver collection contains 45,493 frames; it extends beyond the server counter snapshot. Mixing that denominator with earlier server counters is not exact reconciliation.
- Detailed turn history retains 64 entries. A percentile from that history is a recent-window percentile, not an all-209-turn latency percentile.
- The client deliberately waited for completion plus a **two-second gap** between regular turns. Held imagery is not all attributable to avoidable queued-speech stalls.

There is a small mismatch even between some generated/held component totals and sent counters; they are bookkeeping counters with different update events, not a certified partition of every receiver frame. Do not force them to sum by silently adjusting values. The proposed provenance ledger resolves that gap.

[Ten active TRT calls](../../benchmarks/implementation/calls-h264-trt-c10.json) passed transport/cleanup but recorded **9,153 underrun slots**. That is not ten smooth real-time speakers.

[Final staged C1](../../benchmarks/implementation/calls-final-staged-c1.json) recorded **251 video underruns** and **481,920 held speech-time audio samples**, equal to **10.04 seconds at 48 kHz**. A paced wire FPS near 25 does not negate those stalls.

The short generated-idle success and the longer soak preceded final follow-ups. The fallback C1 test exercised later code but a different memory/backend profile. Neither substitutes for a fresh sustained test of the intended final fast profile.

## Geometry and memory cross-checks

Token counts: 512²→1280; 480×832→1950; 576×1024→2880.

A 24-frame native-portrait RGB chunk uses `24 * 480 * 832 * 3 / 2**20 = 27.421875 MiB`. Two queued chunks plus one current chunk use 82.265625 MiB per peer, or 822.65625 MiB for ten peers, before history/IPC/audio/encoders. These are arithmetic storage sizes, not observed RSS peaks.

480×832 is 15:26, not exact 9:16. The 468×832 delivery crop and native 576×1024 profile must remain separately labeled. Smaller validator-compatible geometry has not thereby passed visual acceptance.

Torch peak counters omit some TensorRT-owned device allocations; post-run device snapshots omit transient peaks. The retained evidence explicitly distinguishes them. Avoid comparing an allocator-only number to total GPU capacity as if it were the entire model footprint.

## Validation disposition

Safe conclusions:

- The first implementation round left substantial additional work; the new plan is actionable and source-specific.
- Native DiT, decoder and recurrent encoder dominate measured chunk cost.
- Queued-turn/admission improvements matter for latency and service behavior even if raw model FPS barely changes.
- Ten simultaneous 25-FPS speakers need ~8.75× the retained native throughput before headroom.
- No current evidence justifies replacing the production MuseTalk renderer with SoulX.

Unsupported conclusions:

- “All optimizations are finished.”
- “TensorRT made the whole model 25% faster.”
- “25 wire FPS means 25 new speech frames per second.”
- “Ten peers means ten smooth speakers.”
- “The same base portrait guarantees the same pose or exact first/last frames.”
- “The generic VAE tiling switch is a ready low-VRAM solution.”

Next step is P0 measurement fixes, followed by separately gated scheduler and GPU experiments—not a production migration.
